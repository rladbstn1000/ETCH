## 3. 대표 사례 1 — 프로젝트 색인 자동 복구

**문제.** DB 커밋 후 이벤트로 ES를 갱신하던 경로에서 ES가 중단되면 원본 변경은 저장되지만 검색 문서는 갱신되지 않았다. ES 재개만으로 복구되지 않아 수동 재색인이 필요했다.

**개인 변경.** 프로젝트 변경과 revision/outbox를 같은 MySQL 트랜잭션에 저장했다. 단일 worker가 최신 DB 스냅샷을 읽고 ES 반영을 시도하며, 실패한 작업은 재시도 시각과 함께 DB에 남긴다. 중복·과거 작업에는 revision 검사를 적용하고, 비공개·삭제 문서는 검색 메타데이터를 제거한 tombstone으로 관리했다. 검색 응답의 공개 여부는 DB에서 일괄 재확인한다.

**검증.** 실제 ES 중단 → 프로젝트 저장 → 미처리 상태의 backend 강제 종료·재시작 → ES 복구를 수행했다. 수동 재색인 없이 DB·ES·실제 검색의 최신 상태가 일치했다. ES 저장 후 outbox 완료 기록 전 종료도 별도로 검증했다.

**한계.** 단일 worker의 at-least-once 최신 상태 수렴이다. exactly-once, 모든 순간의 DB/ES 동기성, 장애 중 검색 가용성, ES 전체 소실 자동 복구를 주장하지 않는다.

**한 문장.** “프로젝트 변경과 검색 반영 작업을 같은 트랜잭션에 기록해, ES 장애와 프로세스 재시작 이후에도 수동 재색인 없이 최신 검색 상태로 복구하도록 개선했습니다.”

근거: [E1](EVIDENCE.md#e1-프로젝트-검색-색인-자동-복구).

## 4. 대표 사례 2 — MySQL 목록 조회 개선

**문제.** 프로젝트 목록을 DTO로 변환하며 작성자를 읽을 때 추가 SELECT가 발생했다. 같은 작성자와 서로 다른 작성자를 나누어 조회하자, 서로 다른 작성자 수에 따라 JDBC 실행 횟수가 증가했다.

**개인 변경.** 해당 목록 Repository 메서드에만 EntityGraph를 적용했다. 전역 EAGER 변경이나 컬렉션 전체 fetch, 메모리 페이지네이션을 도입하지 않고 목록에 필요한 작성자 로딩 범위를 조정했다.

| 첫 전체 페이지의 반환 건수 | 같은 작성자: 전→후 | 서로 다른 작성자: 전→후 |
|---:|---:|---:|
| 1 | 3→2 | 3→2 |
| 3 | 3→2 | 5→2 |
| 10 | 3→2 | 12→2 |
| 30 | 3→2 | 32→2 |
| 100 | 3→2 | **102→2** |

**검증.** 실제 MySQL 합성 데이터, 세 정렬에서 같은 횟수를 관측했다. 동일 158조건의 전체 응답 JSON이 일치했고, 공개·삭제 필터·정렬·자료형·NULL·페이지 계약과 업무 데이터 불변을 확인했다. 관련 테스트 50개 중 MySQL MockMvc의 권한·상세·색인 스냅샷 검사는 5개다. 나머지는 기존 H2·mock 기반 회귀이며 50개 전체가 실제 MySQL HTTP end-to-end 검사는 아니다. 주 계측은 Controller 직접 호출부터 DTO/JSON 변환까지이며 실제 운영 HTTP 지연 측정이 아니다.

**한계.** 페이지 크기 100의 마지막 5건은 서로 다른 작성자일 때 6→1회, 같은 작성자일 때 2→1회이며, 다음 빈 페이지는 모두 2→2회다. 항상 SQL 2회라는 주장이 아니다. Formula 내부 상관 집계 비용과 운영 응답시간은 별도로 남는다. 이전 H2 3건 페이지 7→4회는 중복 좋아요 COUNT 제거라는 다른 개선이다.

**한 문장.** “실제 MySQL 합성 데이터에서 작성자 추가 조회를 재현하고, 목록 전용 EntityGraph로 서로 다른 작성자의 100건 조회를 JDBC 102회에서 2회로 줄이면서 158조건의 응답 계약을 보존했습니다.”

근거: [E4](EVIDENCE.md#e4-mysql-프로젝트-목록-조회-개선). 최신 원본 비교 JSON은 로컬 보관이며 원격 반영 전에 내용과 수치를 대조했다. 이번 문서 작업에서 재측정하지 않았다.

## 5. 대표 사례 3 — 채용·뉴스 증분 동기화

**문제.** 반복 전체 조회를 줄이면서 변경·삭제·재시작·문서별 실패를 처리해야 했다. JDBC의 조회 위치가 앞으로 이동했다고 ES 반영까지 성공한 것은 아니었다.

**개인 변경.** 원본과 같은 트랜잭션에서 ID별 최신 검색 상태, UTC 마이크로초 변경 시각, revision과 삭제 표식을 기록했다. 입력별 checkpoint/PQ/DLQ를 분리하고 겹침을 둔 JDBC 증분 조회를 적용했다. 원본 ID·revision·내용 대조와 현재 DB 기준 repair를 별도로 마련했다.

**검증.** 시험 조건에서 전체 원본 반환 공고 120행·뉴스 121행과 각 1건 변경 시 증분 반환 각 1행을 구분해 측정했다. 이미 읽힌 작업이 PQ에 남은 상태에서 재조회 겹침 범위를 벗어나도록 한 뒤 Logstash를 강제 종료·재생성했고, seed/repair 없이 검색 상태가 회복됐다. Mapping 오류는 DLQ 확인 후 별도 운영자 복구로 검증했다.

**한계.** 행 반환량은 DB 스캔량이나 처리 속도 배수가 아니다. 겹침 밖 지연 커밋, 상태 저장소 손실, 임의 불일치와 DLQ 포화는 별도 대조·복구가 필요하다. PQ 자동 복구와 운영자 repair를 합쳐 모두 자동이라고 설명하지 않는다.

**한 문장.** “채용·뉴스 변경 추적과 JDBC 증분 전달을 구성하고, 전송 장애의 영속 큐 복구와 문서별 오류의 운영자 복구를 구분해 검증했습니다.”

근거: [E2](EVIDENCE.md#e2-채용뉴스-증분-동기화).

## 6. 대표 사례 4 — 검색 평가와 기준선 관리

**문제.** 검색이 실행된다는 것과 적절한 결과가 상위에 나오는 것은 달랐다. 엔진 이관 이후에는 결과 변경이 데이터 오류인지 분석기 변화인지도 구분해야 했다.

**개인 변경.** 작은 합성 코퍼스, 30질의, 관련도 0/1/2와 이유 720개를 평가 전에 고정했다. 실제 API에서 nDCG@5를 계산하고 필터·권한 계약은 별도로 검사했다. 엔진 변경 비교, 동일 엔진 재현성, 승인 기준선을 분리하고 지정된 후보만 활성화했다.

| 평가 종류 | 이전 기준선 | 승인된 새 엔진 기준선 |
|---|---:|---:|
| 채용 관련도순 | 0.932250 | 0.927753 |
| 뉴스 관련도순 | 0.911920 | 0.907424 |
| 프로젝트 최신순 | 0.707469 | 0.707469 |

**검증과 결정.** React 관련 두 질의에서 직접 관련 결과가 2위→3위, 각 nDCG@5가 0.926045→0.881078로 내려갔다. 결과 소실은 없었지만 손실을 기록했고, 알려진 한계로 수용한 특정 후보만 현재 기준선으로 채택했다. 과거 비교 2건 FAIL은 보존했다.

**한계.** 합성·자체 관련도 판정이며 실사용자 검색 정확도가 아니다. 최신순 프로젝트와 관련도순 채용·뉴스 점수는 같은 목적의 순위가 아니다. 엔진 이관을 검색 품질 개선이라고 표현하지 않는다. 승인 대상과 이후 backend 빌드는 구분한다.

**한 문장.** “고정 합성 평가셋으로 검색 결과를 비교하고, 엔진 변경에 따른 두 질의의 순위 손실을 숨기지 않은 채 승인된 기준선과 과거 비교를 분리했습니다.”

근거: [E3](EVIDENCE.md#e3-고정-검색-평가와-승인-기준선).

## 7. 보조 정비와 공개 결과물

권한 전체 허용 제거, 작성자 소유권·비공개 조회 검사, 검색 쿼리·필터·날짜 처리, 오류/정상 0건 구분, 합성 seed와 빈 볼륨 초기 설치, 기존 데이터 이관·복귀, 읽기 전용 로컬 데모 정책을 정리했다. 후속 호환성 검증 기록의 조합은 Boot 4.1.1 / Spring Data Elasticsearch 6.1.1 / Java Client 9.4.5 / ES·Nori 9.4.7 / Logstash 9.5.4다. 이는 당시 검증 조합이며 현재 원격 기본 브랜치의 구현 버전이나 모든 의존성의 보안 완료를 뜻하지 않는다.

공개 체험판은 React·TypeScript·Vite의 별도 정적 빌드와 가상 데이터 공급부를 사용한다. 검색·상세·가상 마이페이지·자기소개서/포트폴리오 편집·스크랩·지원 현황을 체험할 수 있고 변경은 메모리에만 남는다. 추천·채팅은 예시이며 실제 로그인·지원서 제출·업로드·메시지 전송은 제공하지 않는다.

Cloudflare Pages에 검토한 정적 파일만 배포했다. 최신 배포 보고상 production Chrome 8/8, 고유 주소 `/process` 1/1 PASS이며 정상 흐름의 API/OAuth/WebSocket/외부 데이터 호출은 0회다. Chrome 320/390px 검사는 실물 모바일과 구분한다. 최신 배포의 Safari·WebKit·실물 모바일 검사는 미실행이다. [E5](EVIDENCE.md#e5-공개-정적-체험판과-최신-배포)

## 8. PPT·링크형 포트폴리오로 변환하는 구성안

다른 프로젝트와의 분량·순서는 전체 제작 시 결정한다. ETCH 단독 구성안은 다음과 같다.

| 슬라이드 | 핵심 메시지 | 사용할 시각 자료 | 발표 시 보충 |
|---|---|---|---|
| 1. 서비스·역할 | 채용·뉴스·프로젝트를 연결한 탐색 서비스 | 검토한 최신 체험판 홈/검색 화면, 역할 구분 | 팀 구현과 개인 후속 개선, 정적 체험의 범위 |
| 2. 장애 복구 | DB 저장 성공 뒤의 색인 실패도 복구할 수 있도록 설계 | 변경→DB/outbox→worker→ES의 개념 흐름도 | 실제 종료 시점, revision/tombstone, 단일 worker 한계 |
| 3. MySQL 조회 | 작성자 수에 따라 늘던 추가 SELECT를 목록에서 제거 | 반환 건수별 SQL 전후 표 | 실제 MySQL 조건, EntityGraph 범위, Formula 비용 |
| 4. 검증·데모 | 결과와 한계까지 설명할 수 있는 구현 | 증분 반환량·검색 변경 요약·공개 데모 링크 | PQ와 repair 구분, 합성 평가, 과거 FAIL 보존 |

확장판에서는 증분 동기화와 검색 평가를 각각 한 장으로 분리한다. 새로운 성과 수치를 만들지 않고 이 원고와 `etch.json`의 같은 측정 조건을 사용한다.

### 링크형 프로젝트 페이지 순서

서비스/역할 → 화면 체험 버튼 → 개인 개선 요약 → 네 사례 → 검증 조건/한계 → 근거 위치. 공개 화면이 backend를 실행한다고 오해할 수 있는 실시간 상태판이나 성능 배지는 넣지 않는다.

### 시각 자료 준비 목록

현재 공개 요약 URL과 기존 팀 이미지 경로는 사용할 수 있지만, 로컬 검증 스크린샷을 이 묶음에 복사한 것은 아니다. 최종 제작 시 최신 홈·검색·`/process` 화면을 캡처하고 가상 데이터임을 표시한다. 원본 로컬 스크린샷/실행계획은 공개 가능한 부분을 검토한 뒤 사용한다. 새 다이어그램은 실제 관측 화면이 아닌 **설계 설명용 도식**이라고 구분한다. 팀 당시 아키텍처 이미지를 현재 정적 배포 구조로 표시하지 않는다.

## 9. 면접 준비 질문과 답변의 핵심

| 질문 | 답변의 핵심 |
|---|---|
| AFTER_COMMIT 이벤트만으로 부족했던 이유는? | DB 성공 뒤 외부 색인이 실패하면 복구할 영속 작업이 없었다. 동일 트랜잭션 outbox로 재처리 대상을 남겼다. |
| 같은 document ID만 쓰면 멱등성이 해결되는가? | 중복 문서 생성 방지와 과거 쓰기의 최신 문서 덮어쓰기 방지는 다르다. revision·tombstone·현재 DB 상태와 409 판정을 함께 관리했다. |
| PQ가 있으면 모든 누락이 자동 복구되는가? | 이미 읽힌 전송 실패와 애초에 겹침 범위에서 읽지 못한 변경은 다르다. 후자는 대조·repair가 필요하다. |
| 왜 작성자가 같은 데이터와 다른 데이터를 나눴는가? | 같은 영속성 컨텍스트의 작성자 재사용이 추가 조회 문제를 가릴 수 있어 작성자 분포와 페이지 크기를 분리했다. |
| 왜 목록 메서드에만 EntityGraph를 적용했는가? | 필요한 to-one 로딩 범위를 해당 경로에서만 바꾸고 다른 기능의 전역 로딩·응답 계약에 미치는 변경을 줄였다. 실제 SQL로 확인했다. |
| SQL 102→2는 응답시간도 51배 개선인가? | 아니다. JDBC 실행 횟수이며 Formula 내부 DB 작업과 실제 운영 지연은 별도다. |
| 검색 점수가 낮아졌는데 왜 수용했는가? | 중요한 결과가 소실되지 않고 두 질의에서 한 단계 내려간 손실을 확인했다. 기존 FAIL을 보존하고 지정 후보만 수용했다. |
| 공개 사이트에서 장애 복구를 직접 실행할 수 있는가? | 아니다. 공개 사이트는 화면 체험판이며 실제 장애 실험은 로컬 backend 검증 기록으로 설명한다. |

## 10. 다른 프로젝트와 한 번에 제작할 때의 인계문

아래 지시를 전체 포트폴리오 작업의 시작점으로 사용한다.

```text
ETCH는 docs/portfolio-kit/ETCH.md를 공통 원고로,
EVIDENCE.md를 근거·측정 범위 확인용으로,
etch.json을 구조화 입력으로 사용한다.

다른 프로젝트도 목적·기간·인원·내 역할·팀 구현·개인 변경·
문제·판단·구현·검증·수치의 조건·한계·데모·근거 위치를 같은 구조로 정리한다.
다른 프로젝트의 최신 사실은 그 프로젝트 자료를 따로 읽고 확인한다.
ETCH의 지표나 과거 설명을 다른 프로젝트에 복사하지 않는다.

동일 공통 원고에서 PPT와 링크형 프로젝트 페이지를 만든다.
실제 팀 기여와 개인 고도화를 구분하고, 한 슬라이드에 주장 하나를 둔다.
수치에는 환경·대상·단위·측정 구간을 함께 표시한다.
원격 미공개 커밋과 파일은 GitHub 링크로 만들어 넣지 않는다.
화면 체험판과 실제 backend 검증을 구분한다.

전체 코드나 모든 실험을 다시 수행할 필요는 없다.
최신 배포 주소와 사용할 주장에 연결된 로컬 원본만 확인한다.
미확인 사항은 채우지 말고 확인 필요로 남긴다.
```

전체 포트폴리오 제작은 후속 작업이다. 이 패킷의 존재가 PPT·PDF·개인 사이트의 제작 완료를 뜻하지 않는다.
